# LLM 학습 구조 검토

작성일: 2026-09-19. 상태: **검토만 완료, 미구현.** 이 문서의 구조·판단은 제안이며 측정된 성능이 아니다.

## 질문

"LLM으로 학습해서 인식 정확도를 올리는 구조를 만들 수 있나?"

## 결론

가능하다. 다만 핵심은 "LLM이 학습한다"가 아니라 **사용자가 고친 값을 앱이 기억하는 것**이고,
LLM은 그 위에 선택 기능으로 얹는 것이 맞다. 지금 구조를 갈아엎을 필요는 없다.

## 지금까지 확인된 실패 (v0.1.4 기준)

| 실패 | 원인 | 해결 주체 |
| --- | --- | --- |
| `골든애플` → `골든매플` | OCR 글자 오인식 | LLM(문맥 교정) 또는 사람 |
| `메가MGC커피` → `메가MGC커파` | OCR 글자 오인식 | 브랜드 사전 보정(구현됨) |
| `2026.1 2.21` | OCR이 숫자 사이에 넣은 공백 | 규칙(구현됨) |
| 사전에 없는 브랜드 | 브랜드 목록이 코드에 고정 | 교정 기억 |
| 처음 보는 화면 배치 | 규칙이 없음 | 교정 기억 또는 LLM |

실제로 막히는 대부분은 "문장이 어려워서"가 아니라 **사전에 없는 브랜드·처음 보는 배치**다.
이 둘은 LLM 없이도 해결할 수 있다.

## 제안 구조

```
이미지 → 바코드 + 좌표 있는 OCR → 칸 분리          (v0.1.4까지 구현됨)
                 ↓
   1층  규칙 파서            빠르고 무료, 오프라인, 테스트 가능   (구현됨)
                 ↓ 비어 있는 항목만
   2층  교정 기억            사용자가 고친 값을 다음에 재사용     (미구현, 우선순위 1)
                 ↓ 그래도 비면
   3층  LLM 제안(선택)       "확인 필요"로 표시                  (미구현, 우선순위 3)
                 ↓
        사람 확인 → 저장 → 고친 내용을 2층에 적립
```

### 2층: 교정 기억

상세 화면에서 값을 고칠 때 `OCR 줄 → 항목` 한 쌍을 로컬에 저장한다.

- 사용처를 직접 입력하면 그 브랜드를 **사용자 사전**에 추가해 다음 가져오기부터 자동 인식
- 같은 배치에서 반복해 고치면 그 배치용 규칙으로 기억
- 서버·네트워크·비용이 필요 없고 쿠폰 정보가 기기 밖으로 나가지 않는다

### 3층: LLM 배치 선택지

| 방식 | 장점 | 문제 |
| --- | --- | --- |
| 기기 내(ML Kit GenAI / Gemini Nano) | 오프라인, 데이터 유출 없음, 사용료 없음 | 베타이고 지원 기기가 제한적. 미지원 기기 대비 필요 |
| 서버 경유 API | 기기 제약 없음, 성능 우위 | 서버가 필요해 "서버·계정 없음"이라는 제품 전제가 깨짐 |
| 사용자 API 키 입력 | 서버 불필요 | 키 관리·요금을 사용자가 부담. 배포에 부적합 |

API 키를 APK에 넣지 않는다. APK는 누구나 열어볼 수 있다.

기기 내 모델은 현재 구조화 출력(JSON 스키마 강제)을 지원해 응답 형식 깨짐 문제는 줄었다.
지원하지 않는 기기에서는 2층까지만 쓰고 조용히 넘어가야 한다.

근거: [On-device inference (Android Developers)](https://developer.android.com/blog/posts/build-intelligent-android-apps-on-device-inference),
[GenAI Prompt API (ML Kit)](https://developers.google.com/ml-kit/genai/prompt/android)

## 지켜야 할 제약

- **쿠폰 번호와 원본 이미지는 LLM에 보내지 않는다.** 번호 자체가 금전 가치다. 보내는 범위는 상품명·날짜가 담긴 글자 줄로 한정한다.
- **LLM이 지어낸 값을 차단한다.** 반환된 날짜·사용처·상품명이 OCR 텍스트에 그대로 존재하는지 대조하고, 없으면 버린다.
- 저장 전 사람이 확인한다. 값의 출처(규칙 / 기억 / LLM)를 함께 남긴다.
- LLM 없이도 가져오기·비교·제시가 모두 동작해야 한다. 오프라인에서 막히지 않는다.
- 기존 기획서 원칙과 같다. LLM 출력은 검수 후보이며 확정 값이 아니다.

## 측정이 먼저다

현재 검증 샘플은 쿠폰 6장뿐이라 LLM 도입 효과를 판단할 근거가 없다.

1. 사용자가 확인한 값을 정답 세트로 축적한다(OCR 텍스트 + 확정 값, 쿠폰 번호 제외)
2. 현재 규칙 파서의 정확도를 먼저 측정한다
3. 같은 세트로 LLM을 비교한다

이 과정 없이 "좋아졌다"고 판단하지 않는다.

## 파인튜닝을 권하지 않는 이유

샘플이 수십 장 규모라 학습 효과보다 비용·유지보수 부담이 크다.
사용자의 교정 사례 몇 개를 프롬프트에 함께 넣는 방식(few-shot)이 사실상 같은 효과를 내며 훨씬 싸다.

## 권장 순서

1. 교정 기억 저장 구조(2층) — LLM 없이도 이득이 가장 크다
2. 사용자 브랜드 사전 자동 확장
3. 정답 세트와 측정 체계
4. 기기 내 LLM 실험(선택 기능, 미지원 기기 폴백 포함)
5. 필요성이 확인되면 서버 경유 검토

지금 시점의 권장은 1번부터다.
